# FlightHunter V1.0（R3）：验收用例与测试标准

**目的**：给 Codex 可重复执行、能证明行为正确的验收条件。测试的目标是完成一次性完整 V1.0，**不是发布 V0.1–V0.4**。

## 1. 验收分级

- **BLOCKER**：未通过则不得宣布 V1.0 完成；包括错误资格判定、重复提交、隐私外泄、错误时间处理、不安全链接、模拟成功误报。
- **MUST**：核心功能与 UI 的可用性；未通过必须报告并修复，不能以开发时间为由删掉。
- **SHOULD**：质量增强；如某项第三方源受客观限制，应记录实际结果和用户可操作的替代方案。

验收环境：Windows 11 为主；Linux CI 可跑不涉及浏览器私有会话的测试；无需真实敏感身份和真实抽奖帐号即可完成全部模拟站点测试。

## 3. 集成与用户体验测试

### 3.1 全流程模拟

必须提供本地虚拟活动网站与模拟邮件收件箱：

```text
扫描本地官网索引 → 发现候选 → 解析英文/日文规则 → 验证真实性
→ 个人资格过滤 → 按实际价值排序 → 新建报名任务
→ Playwright 预填 → 人工确认按钮 → 模拟提交得到 receipt ID
→ 保存截图/回执 → 定时发布模拟开奖 → 中奖通知 → 兑奖清单
```

**要求：** 每次运行测试必须可重复；不得调用真正航空公司报名接口；不要把 mock success 冒充真实成功案例。

### 3.2 有界的真实网页验证

- 用 10 个可访问的真实活动/历史活动（尽量不同平台）进行**只读和预填前模拟/dry-run**；存在平台条款限制时不得做预填。
- 只有站点规则允许、真实用户明确授权并已完成资格核实，才可测试实际提交，且严守次数限制；不是 V1.0 发布的强制条件。
- 将结果分成 `readable / parsed / prefillable / submission_confirmed`，不同层级分别统计；没有得到真实提交证据不得显示 `submission_confirmed`。
- 遇到地区限制、不可访问、封闭表单，用 fixture 测试代替并写清环境局限。

### 3.2A 行程福利端到端模拟（R2）

`新建2027年日本样例行程→国家/城市匹配→多语言发现优惠与当地活动→官方条款时间窗口提取→三态个人资格→中文使用指南→保存公开券→模拟账户领券→确认券入卡包→时区提醒→用户核销→修改行程重新匹配`。至少包括免费展示券、付费限制券、限量领取券、2027未公布历史活动、动态App券和规则撤销样本；不得将模拟完成误报为真实领取。

### 3.3 搜索来源的验收

- 至少 14 个语言词典组；为每组准备 2 组检索用例，检查动词、奖品、年度替换等模板化功能。
- 官方来源目录目标 100 个**真实且具有抽奖/促销相关性**的网址。若由于客观条件达不到，提供经实际访问确认的数量和缺口，不捏造链接。
- 同一官网内容未变化不反复计费；过期活动不反复推送；异地时区计算准确。

### 3.4 量化的质量目标

使用固定标注 fixture（至少 30 个、约 200 个关键字段）进行离线评估：

- 资格判定 **0 次不确定误报符合**（这是阻断性要求，至少覆盖 T01–T04、T28–T29）。
- 截止日/时区 100% 通过固定边界案例；未知不乱猜。
- 去重：固定同轮重复链接全部正确合并，不同轮次全部正确分离。
- 表单提交幂等：模拟并发和重复任务 100% 不发生超额提交。
- 关键字段准确率目标 >=95%（只统计有明确证据的已核实字段）；达不到则显示未达标，不能改动标注绕过。
- 风险阻断与私密数据泄漏相关的测试必须 100% 通过。
- UI：桌面 1366px 与手机 390px 不发生关键交互被遮挡；提供界面截图供复核。

这些是**交付质量门槛/测试集目标**，不是对真实全球活动识别率或中奖率的虚假保证。

## 4. 代码质量与安全门槛

- `pytest` 全绿，`ruff` 无阻断 lint，`mypy`/`pyright` 对核心领域模型与 API 参数通过类型检查。
- 迁移升级与回滚、恢复备份、跨时区、跨进程幂等均有自动测试。
- CI 中扫描密钥及个人信息泄露（至少提供 `.gitignore`, `detect-secrets` 或同类机制和测试样本）。
- 所有可控外部输入都限制 URL scheme/host、响应体大小、HTML 脚本、PDF 大小和重定向次数。
- 真实浏览器日志和异常报告默认遮蔽用户姓名/邮箱/电话/生日/API Key/验证码。
- 外部登录/支付/上传证件/社媒发帖/营销授权/中奖兑奖回复没有无人值守自动执行路径。
